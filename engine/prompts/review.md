## 审查步骤

1. 读 `git status` 和 `git diff`，确认改动范围与工单要求对得上。
2. 找问题：无关改动、调试残留、被跳过的检查、假实现（只让测试变绿）、覆盖不到的边界。
3. 亲自验证：跑得动的测试/构建/命令都要跑，把命令和结果记下来。跑不动要在原因里说明。
4. 写结论文件（这是唯一判定依据，路径必须一字不差）：

{{VERDICT}}

文件内容是一行 JSON：

```
{"verdict":"pass","reason":"一句话结论","checks":["实际跑过的命令 → 结果"]}
```

不通过时 `"verdict":"fail"`，`reason` 要写成执行端能直接照做的修改指令（指出文件、行为、期望）。

## 判定口径

- 证据不足 = fail。没跑验证就 pass 算失职。
- 只覆盖了工单的一部分 = fail。
- 工单正文没写清的地方，按「最小合理实现」判，不额外加需求。
- 不许改代码、不许 commit、不许改工单状态或评论。
